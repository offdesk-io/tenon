# Tenon

A design system. Code is the source of
truth; the Figma library is a replica built from it, not the other way round.

Tenon is tokens plus eighteen React components. The tokens came first on purpose:
a component built on a set that is still moving has to be rebuilt when the set
settles.

One thing to know about reach. The CSS file works anywhere, so a plain HTML and
CSS project can adopt the tokens today. The React components only reach a React
app. That is an argument for the token layer being the part that matters first.

## Where it came from

Tenon started from a task board's stylesheet that already carried a two-tier
token block: primitives that are ramps with no opinion, semantics that say what
a colour is *for*. Tenon keeps that shape and takes its colour anchors from it,
so that palette survives the move.

The other parent is an earlier design system. Tenon copies its
structure —
nineteen-step ramps numbered 50 to 950, spacing numbered so that 100 is 8px, a
semantic colour layer split into background, text, icon and stroke — and none
of its values.

Two things that system does and Tenon does not. It has 102 component tokens, almost
all of them for the button, and Tenon has none: a component's CSS reads
`var(--tenon-background-accent)` directly, and a component needing a value no
semantic token covers means the semantic layer has a gap to fill rather than a
component token to add. And its semantic colour layer carries fourteen loose
tokens at the top level (`accent`, `border`, `foreground`) that duplicate what
is in the four groups below them. Tenon has the four groups only.

## The two tiers, and what is not in them

Colour and typography have two tiers. Everything else has one.

A semantic tier exists so a value can change between themes while the name
stays put. That is the whole job. A gap of 8px is 8px in dark mode, so
`space/gap/default → spacing/200` would be a rename with a lookup hop attached.
So spacing, radius, border width, breakpoints and icon sizes all read one
`dimension` scale directly, and the rule that nothing reads a primitive applies
to colour, where it earns its keep.

That system is inconsistent in both directions here — its spacing sits in primitives
with nothing above it, its rounding sits in semantics with nothing below it —
and Tenon collapses both onto the single scale. Radius keeps names (`radius.md`,
`radius.full`) because a radius is the one measurement a component should not
pick freely, but those names alias the same scale everything else reads.

The names are also what lets a theme change its corners. A
`tokens/semantic/radius.<theme>.json` points any of them at a different step,
and the build writes those picks at the end of that theme's block, so a theme
can be squarer or rounder while every component reads the same
`--tenon-radius-lg` it always did. The file may only replace names the shared
file already has, which keeps a new radius a decision for every theme at once.
No theme has one yet.

If a compact or scaled density ever arrives, the dimension scale itself becomes
mode-aware. Every `var()` call site stays exactly as it is.

## Colour

Eighteen hues by nineteen steps, plus five values that sit outside the ramps.
Every one of the 347 is generated by `scripts/generate-ramps.mjs` from a single
anchor hex, in OKLCh, so that blue-600 and green-600 are the same weight on the
page. Eleven of the anchors are colours the task board already used; five fill gaps
in the wheel so there is a distinct hue available per bucket as the task board grows.

OFFDESK's brand colours get five ramps of their own, made the same way, for
the two OFFDESK themes further down: `offdesk-orange`, `offdesk-yellow`,
`offdesk-blue`, `offdesk-concrete` and `offdesk-steel`. Seven more carry its
bucket colours 4 to 10, each pinned to its own hex the same way:
`offdesk-cyan` (Blueprint cyan), `offdesk-purple` (Radiation purple),
`offdesk-magenta` (Marker magenta), `offdesk-teal` (Patina teal),
`offdesk-olive` (Workwear olive), `offdesk-kraft` (Kraft) and `offdesk-pink`
(Hi-vis pink). The prefix keeps them
apart from Tenon's own orange, yellow and blue. The method only lands near an
anchor, and a brand hex is not negotiable, so the step nearest each anchor is
pinned to the hex exactly: Safety orange at 500, Signal yellow at 250, IBM blue
at 700, Concrete at 150 and Raw steel at 450. Ink has no ramp of its own. It is
the dark end of Raw steel's, pinned at 950, so the brand's neutrals are one
scale from steel's lightest tint down to Ink. `color.offdesk` names them, so
`color.offdesk.ink` is Ink wherever a theme states a brand role. It also holds
the two values that are on no ramp: Raw steel dark, which falls between steel's
700 and 750 and matches neither, and `ink-raised`, the dark panel colour the
brand's own stylesheet derives from Ink. The brand's white is `base.white`.

The generated ramps are consistent enough to state a rule: **every hue clears
4.5:1 against white by step 550 or 600, and against a dark panel by step 450 or
500.** Picking a colour for text is now a lookup rather than a measurement.

`base.white` and `base.black` are endpoints rather than steps, and keeping them
off the neutral ramp is what stops "the lightest neutral" quietly becoming pure
white. `base.yellow` is pure `#ffff00`, the 1984 theme's accent, kept off the
yellow ramp because no generated step gets near it. `base.urgent` and
`base.soon` are the timeline's overdue and due-soon anchors. The tokens a tag
reads, `status.over` and `status.soon`, take a red and an amber ramp step per
theme instead, since one hex cannot clear 4.5:1 on a light fill and a dark one.

The ten categorical `chart.1`–`chart.10` tokens are one step off ten different
ramps. They do the job the task board's bucket colours do. Each is picked to be
read as text, which is how a chart `Tag` draws it, so a theme may darken or
lighten it away from the colour it is named for. `chart.1-solid` to
`chart.10-solid` are the full-strength colours beside them, for a mark that
carries no words, such as a card's bucket stripe or a legend dot. In light, dark
and 1984 each is the same colour as its `chart.N`; the OFFDESK themes are where
the two part. The build's contrast report leaves the solid tokens out, since it
only measures text, icon and status tokens.

The five status colours — success, warning, error, info and running — are one
family and behave like accent. `background.X` is the solid fill with
`text.on-X` on top; `background.X-subtle` is the tint a `Tag` or a quiet
`danger` button sits on. That rule is what makes a solid green button
buildable from the same tokens that colour a pale green chip. Green and amber
fill at ramp step 600 rather than 550, because at 550 neither clears 4.5:1
under white, and the build measures every `text.on-X` against its own
`background.X` and says so.

`running` is the fifth. It means a queue an agent is working, and it is orange
rather than amber because amber already means warning: a running queue and an
overdue task must not look the same.

## Typography

A size ramp from 10px to 71px. Below `xl` those are the sizes the task board already
uses, rounded off the half-pixels it had drifted into; above it the ratio is
1.2, which is the range a page that is not the task board will want.

Six headings, `heading-1` through `heading-6`, plus stat, body, body-sm, label,
overline, overline-sm, tag, caption, caption-sm and code. `stat` is the figure in a Stat and `tag` the
words on a Tag, and they are the two styles the build writes no class for,
since those components own `.tenon-stat` and `.tenon-tag`. They land at the
small end of the ramp because the task board is a dense UI: `heading-1` is
28px, not 49px. When Tenon goes into a project with room to breathe, the
headings move up the ramp and nothing else changes.

`tag` exists so a theme can give its small labels a voice without touching the
buttons and fields that share `label`. Tag and Pill read all of it, and TagChip
reads its family, spacing and case while keeping its own larger size and a
heavier weight. In light, dark and 1984 it is the mix those components set before it
existed, caption's family, size and line height with label's weight, so they
draw as they did. Case is the one thing a text style cannot say, so it is a
theme token of its own, `text-transform.tag`, kept in each theme's colour file
beside elevation, and TagChip's font is another, `font-family.tag-chip`.

Before the style existed Tag and Pill took their letter spacing and case from
the text around them, and TagChip its font, so a Tag in a Card eyebrow carried
the eyebrow's tracking. Outside OFFDESK those three values are `inherit` so
that still happens. TagChip's button kept the browser's own button spacing and
case, so it reads the two with a fallback of `normal` and `none`, which is
what it gets when they have no value. A custom property set to `inherit` has nothing
to inherit at `:root`, so the `var()` that reads it is invalid when the browser
computes it, and letter spacing, case and font family are all properties that
then inherit from the parent. OFFDESK sets real values, Plex Mono in capitals at
0.1em, and those apply wherever the theme does.

A page that wants its own small labels or metadata to match reads the same
variables: `--tenon-text-tag-family` and its siblings, and
`--tenon-text-transform-tag`. Two more settings sit in the colour file for the
same reason, each the old fixed value outside OFFDESK: `font-weight.tag-chip`,
the chip's heavier weight, which is 500 in OFFDESK because Plex Mono is loaded
at 400 and 500 only, and `letter-spacing.pill-caps`, the tracking on a Pill in
capitals, which keeps the brand's 0.1em in OFFDESK.

`overline` is the label in capitals that names what sits under it: a column
head, a field label, the name of a hero Stat. 12px, bold, 0.03em apart, and
`overline-sm` is the same at 10px for a card's eyebrow. The capitals are part
of the style rather than something each component adds. DTCG's typography type
has no part for case, so it sits under `$extensions.tenon.textCase`, and the
build writes it out as a sixth variable, `--tenon-text-overline-case`, which the
`.tenon-overline` class and every component reading the style turn into
`text-transform`. Figma's text styles carry case as well, so the resolved copy
in `tenon.tokens.json` writes `textCase` beside the other five parts and the
Figma style can match. A theme that replaces a style in capitals has to say its
case again, and the build checks that it does. The OFFDESK themes set both in
Plex Mono at 0.1em, as their tags. Its tracking is
`typography.letter-spacing.caps`, the one step on that scale in `em` rather
than `rem`, so a word in capitals opens in proportion to its own size.

Weights collapse from the task board's thirteen — which included 520, 560, 570 and
680, the kind of value that gets typed once and copied forever — to four, the four Inter is loaded at. Fonts come only from the theme: no
component and nothing in `tn-page.css` names a family, uses the `font`
shorthand for anything but `inherit`, or asks for a weight between those four.
Each reads a text style's `-family` and `-weight` or a font token, so a theme
can change every face in one file, and the build fails on any of the three.
The task board moves from the system font to Inter with 0.20.0 for this
reason: its own text was in the system font and every Tenon component on it in
Inter, so a button and the card under it were two faces.

Text styles are shared by every theme, and a theme can replace some of them.
`tokens/semantic/typography.<theme>.json` holds only the styles that differ, and
the build writes them at the end of that theme's block, so every class and
component that reads a text style follows. Light never has one, since light
is the shared styles, and today only `1984` does: Fraunces for `title`, `stat` and `heading-1` to `heading-5`, Inter for the rest,
and the site's fluid `clamp()` sizes, which sit off the ladder above on purpose.
Inter is Tenon's intended font. `tenon.css` loads it from Google Fonts with an
`@import` on its first line, so an app on light and dark needs no font setup.
A theme's own fonts load from a stylesheet of their own, `dist/fonts/<theme>.css`,
because an `@import` cannot depend on `data-theme`: while Fraunces sat in
`tenon.css`, every app downloaded it whether or not it ever set the 1984 theme.
Each typography file names the fonts it needs under `$extensions.tenon.fonts`,
one Google Fonts family per entry as the css2 address writes it
(`"Fraunces:wght@400"`). The shared file's list becomes the `@import` in
`tenon.css`, and each theme's list becomes its own sheet, so a new theme gets
one by declaring its fonts in its typography file, with no edit to the build or
to `package.json`. A theme may not list a family `tenon.css` already loads.
Storybook imports every theme's sheet from `.storybook/preview.ts`, so it loads
exactly what a consumer would. The trial faces the site really uses stay out of
the repo. Storybook picks them up from a gitignored `.storybook/fonts-private/`
when it is there.

One Figma constraint worth knowing before the library gets built. Figma
variables cannot hold a composite value, so the six headings land there as
**text styles** and the three elevations as **effect styles**. Only the parts
(size, weight, line height, letter spacing) can be variables. The code side
stays one file either way.

## The build, and the check that is the point of it

```bash
npm run all        # regenerate the ramps, then build everything
npm run build      # tokens, then the React library
npm run tokens     # tokens only
npm run check      # tokens quietly plus a typecheck, for a pre-commit hook
npm run dev        # Storybook, localhost:5199
```

`scripts/build.mjs` writes `dist/tenon.css`, `dist/tenon.tokens.json` and one
`dist/fonts/<theme>.css` for each theme with fonts of its own, and refuses to
write any of them if any of nine checks fail: `tokens/themes.json` must list
light first with light and dark as the only automatic themes, every theme in it
must hold light's key set, a theme's typography file may only replace text
styles the shared file has, its radius file may only replace radii the shared
file has and only with a dimension, every `{alias}` must resolve, no semantic
token may alias another semantic token, every font list must name Google Fonts
families and none twice, no component CSS may name a colour primitive, and
every `--tenon-` name a component reads must be one the build emits.

The first is the reason a token pipeline exists here at all. A stylesheet had
`--accent` missing from its dark block for months, used as a `color:` in
twenty-two places and as a border in nine more, and nothing said a word,
because a hand-written stylesheet has no way to know a key is absent. The last
is there because a `var()` naming a token that does not exist falls back
silently and looks completely fine, which has happened twice here.

Contrast reports rather than fails, because `text.disabled` is meant to sit
below AA. It measures every text and icon token against its own background,
every `text.on-X` against `background.X`, which is the only surface an on-X is
ever read on, every `text.X` against the `background.X-subtle` tint a tag sits
on, and `status.over` and `status.soon` against `background.neutral`, where the
urgent and soon tags put them. Measuring the on-X tokens against a page
surface, as it did until v0.4.0, printed ten rows of 1.00 that meant nothing
and hid the one row that did. Since v0.17.0 the disabled tokens are the only
rows it prints, in light and dark.

## Components

Thirty-one: `Button`, `Card`, `Column`, `Badge`, `Tag`, `Stat` and `Field`, then `Modal`, `Textarea`,
`Input`, `Select`, `Spinner`, `Pill`, `Alert`, `Switch` and `SegmentedControl`, then `ToggleGroup`, `ToggleChip`, `StepSlider`, `TagChip`, `Calendar` with its `DateButton`, and `Dropdown` (the task board's bucket tabs, filter chip, Impact slider, task tags, date pickers and Delegate to field), then `Window`, `Markdown`,
`EditableText` and `Disclosure`, then `DragHandle` and `DropLine`, which come with the
`useReorder` hook, then `Menu` and `Toast`. `LinkButton` is `Button`'s anchor form and is not counted
separately. Written in TypeScript so the `.d.ts` gives prop autocomplete in a plain
JavaScript app too.

```jsx
import { Button, Card, Column, Badge, Tag, Stat, Field, Modal } from '@tiagopedras/tenon';
import '@tiagopedras/tenon/tenon.css';        // tokens
import '@tiagopedras/tenon/tenon-react.css';  // component styles
```

**`Card` and `Badge` came from a task board**, not from here. Its
card had already survived five views — the task board, Plans, Execution, Overview
and the queue — which is a harder test than anything Tenon could have given a
card written fresh. So its anatomy is the one Tenon keeps, and what changed is
only the names: `.card` became `.tenon-card`, `--bc` became a local
`--tenon-card-accent` the component sets from its `accent` prop, `cls`/`tag`/
`attrs` became `className`/`as`/spread props, and `position`/`note` became
`lead`/`footer` so nothing in the API assumes the thing on a card is a task.

The one behaviour worth keeping in words: `accent` left undefined draws no
mark rather than drawing a grey one. A grey stripe still reads as a mark, and
the reason to leave it off is that there is nothing to mark. Padding does not
change between the two, so a row of cards lines up either way.

`Badge` is the task board's number badge — a filled pill with a count in it, which
draws nothing at zero and reads `99+` above its max. `Tag` is the chip that
sits in a card's tags row, and it takes either a `tone` or one of the ten
`chart` colours. Those two were both called "badge" by accident; they are
different objects and now have different names.

Every component's CSS reads semantic tokens and nothing else. There are no
component tokens, and the build enforces it: a `var(--tenon-color-*)` anywhere
under `src/` fails the build, because a component naming a primitive is a
component that will not follow a theme.

`Button` has six variants. `primary`, `secondary` and `ghost` start something.
The other three answer something: `confirm` and `destructive` are solid green
and solid red, for the pair of buttons that accept a plan or bin it, where
neither answer should be the quiet one, and `danger` is the tinted one, for a
delete sitting among other controls on a row.

`Column` is the task board's column, where every column in the app is one shape, so the fill, border, radius, gap and both paddings are settled in one place.
That part came across whole. Its head is two groups pushed apart rather than
one row with things floated right: what the column is called sits left, what
you do to it sits right, and neither shrinks the other away.

What did not come across is what those columns mean on that task board. The dashed
edge there says an agent owns the column and you do not drag into it; here
`dashed` draws a dashed edge and the app decides what it means. The orange
tint and turning gear on a running queue became `tone` and a `titleAfter`
slot, so the icon belongs to the app. Keep the dash to one meaning per app and
it keeps reading.

`layout="prose"` is for a column of paragraphs rather than a column of cards:
their own margins do the spacing and the edges get more room. `collapsible`
draws the whole thing as a `<details>` whose `<summary>` is the same head, so
nothing about a column changes by being foldable except the element it is made
of. `ColumnEmpty` is what a column draws when there is nothing in it, and
`boxed` is for a wide one, where a single faint line reads as a column that
failed to load.

`Stat` is the task board's StatCard: one number, boxed, with what it counts under
it. It was three spans scoped to the Reports view until it was pulled out, so
the shape the task board uses for "the answer to the question you opened this view
for" could not be drawn anywhere else.

Two props on `Card` exist because the task board's plan card needed them and the
first port did not have them. `eyebrowEnd` pushes something to the right-hand
end of the eyebrow row, where the plan card puts how far the agent got.
`titleAs` sets the title's element, a div by default, because a card in a list
of cards is usually not a section of the document — pass a heading where it
is. Nothing is styled off it; the page outline is what cares.

A `Card` with `interactive` and a control inside it needs the control to call
`stopPropagation`, or the card's own click fires too. The task board's plan card
has always done this for its link back to the task.

`Field` owns its label, hint and error together. A bare input with the label
wired up somewhere else is how a form loses its labels, and `aria-describedby`
points at whichever note is actually rendered rather than at an element that
might not be there.

```bash
npm run dev     # Storybook, localhost:5199
```

There is one `stories/<Component>.stories.tsx` per component. The toolbar's theme
switch sets `data-theme` on the root, and the stories render against the built
`dist/tenon.css`, so `npm run dev` builds the tokens first. A new component gets
a story file in the same commit.

Above the components, Storybook's Tokens section has five pages, in
`stories/tokens/`: colour primitives, theme colours, typography, dimensions and
elevation. They draw every token from `dist/tenon.tokens.json`, and read the
source files in `tokens/` only for which primitive a token aliases, so a token
change shows up there after `npm run tokens` with nothing to edit. The theme
colour and elevation pages paint every theme in `tokens/themes.json` side by
side by setting a theme's resolved values as custom properties on a wrapper,
which is why they read the same whatever the toolbar is set to. The toolbar's
switch reads the same list, so a new theme gets its column and its switch entry
from the build's own file.

**0.21.0 adds the highlight and spotlight colours.** They are the last of the
task board's own colours, from its focus prompt and the ring round a card being
held. `highlight.from`, `highlight.to` and `highlight.end` are a warm gradient.
`spotlight.*` is a set of eleven for a panel that stays dark in every theme, light
and OFFDESK included, which `background.inverse` cannot be, since it turns
light in dark mode. Each is the same in all five themes. Nine sit on ramp steps
within a few points of the board's values, and two, `base.glow` (#f0b355) and
`base.spotlight-error` (#d98b86), are new literal primitives because no step
comes near them. The build's contrast report now measures the spotlight's text
colours against its own surface, and all of them clear 4.5:1.

**0.20.0 moved the task board's own decisions in.** The task board had kept a
layer of its own over Tenon's components, about 400 lines of it, and a second
app on these components looked nothing like it because none of that layer
reached it. Those values are Tenon's now, snapped to the dimension scale and to
the four loaded weights, so both apps draw the same column and the same card.

- `Column`'s head is set in `overline`, its shadow is `overlay`, it is at least
  120px tall, and its hint, description and chevron are larger. `dropState`
  (`'accept'` or `'deny'`) outlines the body while something is dragged over
  it, in the accent or in red for a column that will refuse what is in the air.
  `ColumnEmpty boxed` sits on the page fill and reads left to right.
- `Card`'s accent stripe moves to the outer edge, over the border, and its
  corners follow the card's own curve. The eyebrow is `overline-sm`, the lead,
  meta and footer are 12px, and the summary sits further down at a looser line
  height. `selected` outlines a card in the accent, for one picked out for an
  action about to happen to it. Its padding is unchanged, so a dashboard's
  agent cards keep their size and gain only the larger small text and the new stripe.
- `Button` gains `outline` (secondary with no fill) and `dashed` (the same with
  a dashed edge, for a button that adds something), `pressed` for a toggle that
  is on, which sets `aria-pressed` too, and `block` to fill its row. `sm` keeps
  12px text.
- `Badge`'s number is 12px. `Stat` takes `size="hero"`, the one figure a view
  is opened for: title-sized, named in `overline`, on the page fill and as wide
  as its content. The default size is unchanged for a row of them.
- `Field`'s label is `overline` in the faint colour. `Input` takes `size="sm"`,
  32px, to sit beside an md `Button` in a toolbar. `Field` and `Textarea` now
  hide under the `hidden` attribute, which their own `display` used to beat.
- `SegmentOption.separatorBefore` draws a hairline before an option, to split a
  row of views into groups, and is dropped on a phone.
- `Menu` is a list of actions under a button, the board's Data menu:
  `<Menu trigger="Data" align="end">` holding `Menu.Item` with an `onSelect`, and
  `Menu.Divider` with an optional `label` for a second half that answers a
  different question. `Dropdown` picks a value, and this one does things.
- `Toast` is a short line that lands where the eye already is: render one
  `<Toaster/>` near the root and call `toast(text, { tone })` from anywhere,
  with `default`, `warning`, `error` or `success`. The default is the inverse
  panel, and a failure is never drawn like it.

Three new tokens came with them: `layout.column-width` (320px), `elevation.popover`
(the menu and toast shadow, none in OFFDESK) and `brand.ink`, the colour a
wordmark is drawn in. `chart.1-strong` to `chart.10-strong` are each chart
colour one step deeper on its own ramp, for a mark that sits on its chart
colour, such as a sub-task bar inside its task's bar.

**The last seven came from two apps that had each drawn their own.** The chat
engine supplied the `Modal` (its window), `Textarea` (its composer), `Spinner`
(its working mark), `Pill` (its tool-call chip) and `Alert` (its permission
prompt). A dashboard app supplied `Switch` and `SegmentedControl`, and
its detail and log sheets are the same shape as the chat's window, which is
why `Modal` is written for both. Neither app loads them, because both are
plain JavaScript with no React, and the chat engine is dropped into hosts it
does not control, so it cannot require one. For now they are where the anatomy
lives once: a change to how a switch or a dialog looks is made here, and the
apps' own copies follow it by hand until they are rebuilt on React.

`Pill` is `Tag`'s outlined counterpart. A `Tag` is a filled chip in a row of
labels; a `Pill` is drawn round something that happened or a state something
is in. `Modal` closes on Escape, the X and the scrim, keeps Tab inside the box
and gives focus back to whatever opened it, and it renders into `document.body`
so no ancestor's `overflow` or `transform` can clip it. Its four sizes are
400, 560, 760 and 912px. The plan modal in that task board is the most developed
of the three it came from, so `Modal` also takes `resizable` (drag the corner,
and `resizeKey` keeps the size for next time), `layout="split"` with
`ModalPane` columns that each scroll and stack on a phone, `initialFocus="footer"`
for a confirmation whose first answer is the safe one, and `onSubmit` for ⌘↵
from inside a text field. `Switch` is for a setting
that applies the moment it flips; one that needs a Save is a checkbox in a
`Field`. `Textarea` is the bare control; with a label, use `Field` with
`multiline`.

**`Input` and `Select` are `Textarea`'s siblings**, added in v0.18.0 for a task
board's settings pages. `Input` is one line of text, in the types that are one
(`text`, `email`, `number`, `search`, `url`, `tel`, `password`), so a checkbox is
never drawn as a text box. `Select` is the native select in the same skin with a
chevron added, because the list the system opens already has the keyboard and
screen reader behaviour a hand-drawn one would have to copy. Its options are
plain `<option>` children; a list whose options carry an icon or sit under a
heading is a `Dropdown`. All three bare controls share a skin and start 40px
tall, so a form mixing them reads as one set. `Input` has a read-only look,
which keeps the text at full strength and drops the white fill. A select has
no read-only state in HTML, so a value that cannot change is text or a disabled
select. With a label, `Field` draws the input already and takes `select` for
the other, with the options as its children. `Field`'s controls keep their own,
slightly tighter skin, so a page uses either `Field` or the bare controls for a
group of fields rather than mixing the two in one row.

**The last four came from the chat window becoming React.** The chat engine's window was
plain JavaScript that drew its own dialog, and rebuilding it on Tenon's components showed
what Tenon did not have yet. `Window` is `Modal`'s counterpart for a panel the page places:
no scrim, dragged by its head, resized from any edge or corner, stacked by the page,
grown out of the thing that opened it and shrunk back into it on the way out. It takes
`rect` and reports `onRectChange`, and it never decides where it sits, so a grid of
windows, a parked position and a saved layout all stay the page's business. Several can be
open at once and only the `active` one answers Escape. `Markdown` renders the subset a
model's reply uses (paragraphs, lists, headings, fenced code, and code spans, bold, italics
and bare links inside them) as React elements rather than an HTML string, so there is
nothing to escape and nothing to inject; what falls outside the subset shows as written.
`EditableText` is a name that becomes a field on double-click, and marks itself with
`data-tenon-editing` so a `Window` around it leaves Escape and drags alone. `Disclosure` is
the quiet summary line that opens into more, with the arrow always drawn.

Four smaller additions came with them. `Modal` takes `bare` (and so does `Window`), which
drops the body and footer's padding and layout for content that arranges itself, a
transcript over a composer; and it now leaves focus where it already is inside the box
rather than moving it to the box, so an `autoFocus` field keeps it. `Spinner` takes
`variant="glyph"`, the cycling asterisks the Claude CLI draws while it thinks, which hold
still under reduced motion. `LinkButton` is a link that looks like a `Button`, for something
that goes somewhere rather than doing something.

**`Spinner` draws a thinking orb by default since v0.16.0.** The chat engine had
already swapped its ring for the dotted spheres from
[thinking-orbs](https://libraries.dev/orbs) (MIT, Jakub Antalik), and making the
orb Tenon's default means every app picks it up on its next tag with no code
change. `variant="ring"` and `variant="glyph"` still draw what they did. `state`
picks one of the orb's nine animations, for a caller whose spinner follows
what a run is doing. Unless asked it is `solving`, the one the chat engine draws
while a run thinks, because `working`, the library's own default, is a loose
scatter of dots that does not read as a sphere at 12px. The orb keeps the ring's box at each
size, 10, 16 and 32px, and draws its canvas a quarter larger and centred over
it, at 12.5, 20 and 40px, because the sphere fills only about 80% of its canvas.
The dots come out the ring's width and nothing beside them moves. The library
tunes three designs, at 20, 32 and 64px, so `sm` and `md` draw the 20 and `lg`
the 32. Its ink is the accent text colour, read off the span at runtime because
the library takes an `rgb()` string and cannot read a custom property. Whether
it sits on a dark page is read off `--tenon-background-default`, which is how it
knows 1984 is dark. Under reduced motion it holds a still frame by itself.
thinking-orbs is Tenon's one runtime dependency, left out of the bundle so an
app that also loads the chat engine gets one copy.

**Drag to reorder is one hook and two small pieces**, added in v0.8.0 so two apps drag the same way. `useReorder({ keys, onMove,
axis })` hands back, per item, `handleProps` for whatever it is picked up by and
`itemProps` for the item itself, plus `listProps` for the list around them. Spread
`handleProps` on a `DragHandle` to pick an item up by a grip, which the dashboard needs
because its rows already use a plain drag to paint hours, or on the item itself to pick
up the whole thing. The picture under the cursor is always the whole item. The fade on
what is being carried waits a tick after the drag starts, because the browser takes its
picture just after that and would otherwise take a faded one. Where it will land is a
line in the accent with a dot at each end, the task board's drop line: `DropLine` as an
element a list inserts between items, or drawn on the hovered item itself through
`data-tenon-drop`, which is what a grid of cards needs. Set `--tenon-reorder-gap` on
the list to the gap between its items and the line sits in the middle of it.
`reorderKeys` and `applySavedOrder` are the two sums around it: where a key goes after
a drop, and how a saved order sorts a list that has grown since. The hook reorders one
list. Moving between lists, like the task board's columns, stays with the app, because the
rules for what may go where are the app's. There is no keyboard way to reorder yet.

**`bindReorder` is the same thing for a list built as an HTML string**, added in
v0.9.0 because plenty of apps are plain JavaScript that a React hook cannot
reach. `bindReorder(list, { onMove, axis, grip, item, keyOf })` binds once to the list
element and returns a function that unbinds it. Its listeners sit on the list rather
than on each row, so the list can redraw its rows after every move without binding
again. Rows carry `data-tenon-reorder="key"` and a drag starts only from a grip,
`[data-tenon-grip]` unless told otherwise, which `dragHandleHTML()` emits: the same
markup as `<DragHandle/>`, character for character. The hook and this function share
their rules in `reorderCore.ts`, so the drag picture, the late fade, which half of a row
the pointer is in, the drop line and the event stopping at the list are written once.

Storybook and the token preview both carry no hard-coded values, so
anything that looks wrong on either is a token that is wrong or missing. That
is how the `--tenon-color-background-default` naming mistake was caught: the
preview had been rendering on browser defaults and looked plausible.

## Using it

```css
@import "@tiagopedras/tenon/tenon.css";
```

`:root` carries light. Dark applies when the system asks for it, unless
`[data-theme="light"]` is set, and applies unconditionally under
`[data-theme="dark"]`. A manual toggle needs no rebuild. Light and dark are the
only automatic themes, and `tokens/themes.json` lists the rest. Each of those,
`1984`, `offdesk` and `offdesk-dark` today, is never automatic: it applies only under
`:root[data-theme="<name>"]`, written with `:root` so it outranks the automatic
dark rule on a system set to dark. Adding one is a line in that list and a
`tokens/semantic/color.<name>.json` holding light's keys, and the build writes
its block and checks it like the others.

An app that sets a theme with fonts of its own imports that theme's sheet
after `tenon.css`. Today that is 1984, which adds Fraunces, and the two OFFDESK
themes, which add Archivo and IBM Plex Mono:

```css
@import "@tiagopedras/tenon/tenon.css";
@import "@tiagopedras/tenon/fonts/1984.css";
```

Until v0.19.0 `tenon.css` loaded Fraunces itself, so an app on the 1984 theme
that upgrades past it falls back to Georgia for the serif styles until it adds
that line.

```css
.card {
  background: var(--tenon-background-raised);
  border: 1px solid var(--tenon-stroke-default);
  border-radius: var(--tenon-radius-lg);
  padding: var(--tenon-dimension-200);
  box-shadow: var(--tenon-elevation-raised);
}
```

Text styles come as five variables each and as a class:

```html
<h2 class="tenon-heading-2">Design oversight</h2>
```

## The OFFDESK themes

`offdesk` and `offdesk-dark` dress Tenon as OFFDESK, so the agency's board and
its client screens can be built from the same components as everything else.
They translate OFFDESK's own brand stylesheet and its `DESIGN.md`, and each
token says either which brand role it is or, where the brand is silent,
"Derived" and what it was worked out from. Brand roles read the brand hexes
by name from `color.offdesk`. The surfaces and greys in between, such as a
hover fill or the faint text colour, come from the brand's own ramps:
Concrete's for surfaces near Concrete, and Raw steel's for surfaces near Ink
and for text. Only these two themes read any of it.

The rules that make it look like OFFDESK are carried by the tokens. Actions and
links are Ink in the light theme and Concrete in the dark one, because the brand
never makes a button orange. Safety orange is the highlight instead, in both
themes: the focus ring, the selected marker (`stroke.accent`) and, as a tint,
the fill behind a selected item. The brand's own stylesheet draws focus in Ink,
so the focus ring is the one place the themes depart from it on purpose.
Borders are Raw steel. The ten bucket colours are OFFDESK's own. The first
three are the brand's yellow, blue and orange; the other seven, cyan, purple,
magenta, teal, olive, kraft and pink, extend them for a board that needs ten
buckets. As text each sits at the step of its own ramp nearest its hex that still
reads on the page, which is a darker step on Concrete and a lighter one on Ink,
and its `-solid` twin is the hex itself in both themes, so a card's stripe shows
the colour the bucket is named for. Every corner is square
except `radius.full`, which stays round so a status dot, a switch thumb and a
spinner still read, and there are no shadows. OFFDESK has no status colours, so
success, warning, error, info and running take Tenon's own ramps, stepped from
the light and dark themes' picks until they clear the same contrast rules.

Type is Archivo, with IBM Plex Mono for captions, small labels and code, at the
brand's weights and letter spacing. Sizes and line heights are Tenon's own,
because these themes dress dense app screens such as the board, where the
brand's page sizes (a 17px body, 32px headings) read bulky. Those page sizes
live in OFFDESK's own brand stylesheet, for documents and marketing pages. Tags,
pills and tag chips follow the brand's label rule: IBM Plex Mono in capitals,
12px with 0.1em tracking, through `text.tag` and `text-transform.tag`. Buttons,
field labels and running text stay in Archivo. The one thing the brand sets
that has no place here is the width axis that makes its display cut wide.

The fonts are opt in, like every theme's. `tenon.css` loads only Inter, so a
page using an OFFDESK theme imports that theme's own font sheet beside it:

```js
import '@tiagopedras/tenon/tenon.css';
import '@tiagopedras/tenon/fonts/offdesk.css';       // Archivo and IBM Plex Mono
// or '@tiagopedras/tenon/fonts/offdesk-dark.css', the same two families
```

## Getting it into a project

Tenon is a public repo with no npm publish behind it, so a project installs it
as a git dependency at a tag. A tag rather than a branch: a branch reference
moves under you on the next `npm install` with no diff to show for it.

```bash
npm i github:tiagopedras/tenon#v0.7.0
```

npm runs no build on a git dependency, which is why `dist/` is committed.

```js
import '@tiagopedras/tenon/tenon.css';        // tokens, everything needs this
import '@tiagopedras/tenon/fonts/1984.css';   // only if the app sets data-theme="1984"
import '@tiagopedras/tenon/tenon-react.css';  // component styles
import { Button, Card } from '@tiagopedras/tenon';
```

Moving a consumer forward means editing its own `package.json`, which is the
point of pinning.

There is one route. Built CSS is never copied into a consumer.

`DESIGN.md` at the root is for an agent building a page somewhere with no
Tenon setup to copy from. It links Tenon's own CSS from jsDelivr at a tag and
adds one small page layer, `design-md/assets/tn-page.css`, which reads only
Tenon's tokens and is exported as `@tiagopedras/tenon/tn-page.css`. Both ship
from v0.17.0. `design-md/README.md` explains how it was built and what has been
checked.

The page layer is also where an app screen's frame lives, and 0.20.0 gave it
the task board's. `tn-appbar` is the bar along the top, a sibling of the page
rather than inside it, so its fill and rule reach both edges of the window.
`tn-page--full` is the page without its 1280px cap, and it is the board's
sideways scroller: the whole region under the bar scrolls, where a board inside
a capped page was a box that cut its own columns off. `tn-frame`, on `<body>` or
an app's root, makes that region run to the bottom of the window, so a board's
columns run full height. `tn-board` lays its columns out at 320px or more with
a 12px gap, all the board's height; set `--tn-board-columns` to the count so the
scroll ends a gutter past the last one. Below 640px each column is the width of
the screen and snaps, and `tn-tabbar` is the phone's bottom tab bar. A board
shown as one part of a page, such as a preview, is `tn-board--contained`, which
is how `tn-board` behaved before.

```html
<body class="tn-shell tn-frame">
  <header class="tn-appbar">
    <a class="tn-identity" href="/">App</a>
    <span class="tn-appbar-spacer"></span>
    <button class="tenon-button tenon-button--secondary tenon-button--md">Data</button>
  </header>
  <main class="tn-page tn-page--full">
    <div class="tn-board" style="--tn-board-columns: 7">
      <section class="tenon-column">…</section>
    </div>
  </main>
</body>
```

## Releasing

```bash
npm version patch         # or minor
npm run all               # rebuild, so the stamp matches the new version
git commit -am "chore(tenon): build vX.Y.Z"
git tag vX.Y.Z && git push --tags
```

## What changes cheaply and what does not

Adding a hue, a step, a semantic token or a theme is an edit and a rebuild.
Changing an anchor hex moves all nineteen of that hue's steps at once, which is
visible but contained.

Renaming a semantic token after an app consumes it breaks every `var()` that
reads it. So the semantic names are worth arguing about now, and the primitives
are disposable: nothing outside `dist/tenon.css` should ever name one.
